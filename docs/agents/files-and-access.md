# File access, worktrees and web auth

## Worktrees and project grouping
- `lib/worktree.ts` resolves linked worktree top-levels to the main repo `projectRoot`; `listAllSessions()` attaches it to each `SessionInfo`, so a repo's worktrees group together in the sidebar. A session whose cwd is a removed worktree is inferred back into the main project, never a phantom project row.
- `/api/worktrees` serves worktree operations under the same allowed-root rules as `/api/files`. New worktrees go under `<repoRoot>-worktrees/<sanitized-branch>`; an existing branch is reused, else `git worktree add -b` creates it. Removing a dirty worktree answers `409 { dirty: true }`, and the UI asks before retrying with `force`.
- git prints POSIX-style absolute paths even on Windows: every path read from git goes through `toNativePath()` (`lib/paths.ts`) before it is compared or returned, and paths are compared with `samePath()`, never `===` (otherwise `isTopLevel` is always false on Windows and the worktree switcher hides). Branch names are not paths and keep their forward slashes. Browser code cannot apply Node path rules, so `/api/worktrees` resolves `currentWorktreePath` server-side and the sidebar uses it for highlighting and the removal fallback.

- A subdirectory keeps its own project identity even though Git can list the containing repo's worktrees. In `SessionSidebar.projectFor`, only an `isTopLevel` worktree cache may lend its identity to other listed paths. Otherwise selecting a repo session from a benchmark subdirectory can be undone by a stale-cache cwd notification, clearing `?session=`.

## File access allow-list
- `/api/files` is not a general filesystem browser. Allowed roots: session cwds, their resolved project roots, and roots added with `allowFileRoot()`, which `/api/cwd/validate` and `/api/worktrees` call when they make a location browsable. "Use default directory" too: `/api/default-cwd` only creates `~/pi-cwd/YYYYMMDD`, and the sidebar selects it through `/api/cwd/validate`.
- `isPathWithinRoots()` (`lib/path-security.ts`) is the single implementation behind `isFilePathAllowed()` and is the security boundary: keep it the only one. It re-resolves and case-folds both sides, so either path form authorizes; roots are stored slash-normalized only as a Set-key convention.
- `isExistingPathWithinRoots()` refuses any path with a `..` segment (`hasParentDirectorySegment()`: authorization collapses `..` before following links, the filesystem after). Query-string and body paths reach that check verbatim. In `/api/files/[...path]` URL parsing drops literal `..` segments, and the route itself refuses an encoded slash inside a segment (`link%2F..%2Fx`), because a session-referenced file skips the existing-path check.
- `/api/files/...?sessionId=` also reads (never lists) a file outside the roots when that exact path appears in the session, so a chat link opens (`lib/session-file-references-core.ts`). Never counted: transcript system messages, the codemode script store, `context_edit` replacements, and the result of any tool but pi's coding tools and the subagent tools (MCP, codemode and third-party extensions relay remote-controlled text). Such a result still authorizes its `details.fullOutputPath` and the arguments of the coding-tool calls it made through `ctx.executeTool()` (`nestedCalls`), never those of its nested MCP calls. User and assistant messages, the model's own tool-call arguments (MCP calls included) and the other entries count. Tools are matched by name: keep the list in step with `CODING_TOOL_NAMES`.
- A UNC cwd (`\\host\share\dir`) must survive the `/api/files/[...path]` round-trip: `encodeFilePathForApi()` folds the `//` root into the first segment (`%2F%2Fhost`) and `filePathFromApiSegments()` decodes it back. Never split a UNC path into segments and rejoin them: `\\host\share` becomes a relative-looking `host/share` and every allow-check answers 403.
- What `type=list` leaves out is visibility, never access: hidden entries stay readable by path. `lib/file-tree-visibility.ts` asks one `git check-ignore --no-index --stdin` per listing, then one `git ls-files` which matched names hold a tracked path; those stay listed. Never let check-ignore consult the index (one whole-index scan per name). `.git` and `.DS_Store` are always hidden. The fixed name list (`node_modules`, `dist`, `build`, …) applies only where Git has no view: outside a work tree, when git fails or times out (5 s), and inside an ignored directory with nothing tracked below it. Names go to check-ignore as `./name` and to ls-files under `--literal-pathspecs`. Both calls pass `-c core.fsmonitor=false`, or expanding a folder runs a hook the repository configured.
- A directory link (symlink or Windows junction) is authorized by where it resolves (#748): one inside a root that leads outside every root is listed but refused beneath it. Never authorize the lexical path: a link committed to a cloned repo would expose `~/.ssh` or `/`. The listing reports its target as `outsideLinkTarget`; the explorer's "Allow browsing" posts `?type=allow-link` with it. `checkLinkedDirectoryApproval()` (`lib/linked-directory.ts`) requires the link's directory to be inside the roots after resolving links and the link to still point where the operator was shown; the route then `allowFileRoot()`s the target until the server restarts — the grant `/api/cwd/validate` gives any directory, so it widens nothing a caller could not already reach. A target that contains a root or the home folder (`/`, `~`, a parent of the project) is listed with `outsideLinkEncloses`, and the explorer confirms before allowing it.

## Explicit original-video reads (01–09 resolved)

[F40](../branch-features/video-attachments.md) reuses the existing upload POST/skip path and authorized cwd. VideoAttachmentPicker.select is the single chooser/drop validation path; skip explicitly references the existing file/current bytes. Plain paths/@mentions and session-text preview exceptions never authorize media transmission. Native user piWebVideo plus current effective SDK projection is required. Reads use existing roots/current authorized cwd, lexical and realpath/link checks, canonical regular-file bounded reads, matching suffix/MIME and MP4/AVI signatures. No roots, upload routes, asset store, transcoding or SDK/global-config changes.

Application limits are 20 MiB/file and complete 32 MiB/request (all effective video Base64, text/images/system/tools/results plus 64 KiB wire reserve), not gateway maxima or the ordinary upload limit. Every request/cold follow-up/tool continuation/queued consumption rereads current bytes and permissions. Missing or invalid effective media stops the whole request, never strips media or falls back to text. Compacted-out/sibling owners are not read; copied sessions do not copy/freeze files or grant access. Restored drafts repeat all checks. See [public acceptance](../branch-features/video-attachments-acceptance.md) for chooser/drop, retries, compaction/branches/queues/modes and historical network evidence; unsent draft/unknown snapshots remain page-local, not durable assets.

## Task directory references (ticket 01)
- `validated-cwd.ts` separates lexical `normalizeCwd()` from existence/type-checking `validatedCwd()`. Tasks with a new UUID still validate the current directory and resolve the project, without `allowFileRoot()`. An already committed UUID confirms its immutable creation fingerprint inside the store lock; it does not stat or re-resolve the directory. Deleted directories or changed worktree ownership cannot turn a lost-response retry into a new task or a file-access grant.

- F33 task project selection merges session metadata and task project references, without `/api/cwd/validate` or `allowFileRoot`. Project changes re-resolve authoritative scope and bind the detach set to a preview; commit is atomic with relationship departures. DirectoryPicker can create a directory, but its portal submit must stop propagation to the enclosing task-creation form. See `docs/branch-features/task-projects.md`.

## Task session scope (ticket 04)
- Source creation and batch links resolve current project identity with awaitable `resolveProjectAuthoritatively` (same existing Git/worktree/subdirectory/removed-path rules, no sidebar display cache). Reusing an A checkout path for B cannot authorize a link to A; the SWR display contract remains unchanged. Exact committed source-create fingerprint retries are checked before any source lookup, including after deletion.
- Native IDs are lookup values, not client paths. Header/stat-only metadata and warm header/name do not hydrate transcripts, start Agents or grant `allowFileRoot`. One locked board validates the full batch and unique ownership before writes. No-project only accepts the reserved chat workspace; Windows identity normalization is server-side. Session cwd/history/tool/model selection remain unchanged.

## Uploads and chat drops
- The explorer's Upload button and a non-image file dropped onto the chat share one client, `uploadFiles()` (`lib/file-upload-client.ts`), and the one endpoint, `POST /api/files/<cwd>?type=upload`; never add a second write path for drops. The explorer asks `upload-check` first and lets the user replace or skip; a chat drop goes straight to `conflict=skip`, so it never replaces a file. It then inserts `@name` for every file the response lists as uploaded *or* skipped (a skipped name is a file already there, often the very file dragged out of the project) and says in a notice that the mention points to the existing file.
- `splitDroppedItems()` routes MP4/AVI suffixes or `video/*` MIME to the single MP4/AVI picker (F40), before checking images. Invalid candidates get an error, never an ordinary mention or a disguised image. `ChatWindow` only forwards the candidates through `ChatInput.addVideos`; it has no second video uploader. Dropped images still attach to the prompt; other empty-MIME/non-MP4/AVI names remain ordinary files. Folders are left out with a notice: the endpoint writes flat file names only (`validateUploadFileNames()`), and the browser cannot tell where a dropped file lives on disk, so the copy always lands in the cwd root.

## Web password throttling
- `lib/auth-throttle.ts` is deliberately global, not per-IP (its header says why). Failures double the delay (1 s → 60 s cap) for everyone; a success or 5 idle minutes resets it. The reset window must stay longer than the max delay, or waiting out one block restarts the burst.
- State lives on `globalThis` under `Symbol.for("pi-web:auth-throttle")`, so it survives hot reload and `proxy.ts` and the route handlers share it under both `next dev` and `next start`. Tests reset it with `recordAuthSuccess()`.
- `POST /api/web-auth` and every `Authorization: Basic` header on `/api/*` share the counter; `proxy.ts` checks Basic before its `/api/web-auth` exemption, so `GET /api/web-auth` is no unthrottled password oracle. A valid session cookie is checked first and never blocked. While blocked, Basic gets `429` even with the right password, and a Basic success never resets the counter (`proxy.ts` explains both).
