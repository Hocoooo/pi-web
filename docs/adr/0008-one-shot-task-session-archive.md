# 0008 — Confirm one-shot task/session archive batches with durable receipts

Task Dashboard archiving now explicitly previews and archives the current linked session families, with additional consent if another task owns any affected family member. Keep task and session visibility as independent states: later links/forks do not automatically archive, and restoring a task does not restore sessions or undo existing manual archives.

Retain the existing two locked metadata files instead of migrating the board and native catalogue into one database or issuing client-side per-session writes. Reserve a fixed pending intent in the board first, then apply the entire session batch and its latest-per-task receipt in one atomic sidecar write under board → session locks; finish the board receipt afterward. This is deliberately not a cross-file transaction: pending remains discoverable and explicitly retryable, while a committed sidecar receipt prevents restart/lost-response retries from re-archiving sessions the user subsequently restored. Scope/ownership epochs fence first application; a later task archive/restore replaces the old intent.

The board keeps v7 with a strictly validated optional cascade domain inside archiveReceipt (older readers refuse it); session metadata reads existing v1 and writes v2 with batch receipts only on first cascade. This persistent format cost is preferable to an unbounded operation journal, automatic rollback of user visibility choices, or treating an archived task as a permanent execution/archive policy. See [feature contract](../branch-features/task-session-archive.md) for recovery and validation limits.
